# M0 — The Instrument

**Goal:** a PNG of an fBm noise field over a hex grid, reproducible from a seed.

No terrain, no world. M0 exists to prove that the coordinate maths, the grid
storage, the RNG and the renderer all work — because every later stage is
debugged by looking at output from these four things. If the instrument lies to
you at M1, you will spend a week blaming your elevation code.

Deliverables: `hex.rs`, `grid.rs`, `rng.rs`, `render/png.rs`, a CLI that takes
`--seed` and `--out`, and the golden-seed test.

---

## Pin the conventions first

Most hex bugs are convention drift — code written under two different
assumptions about which way the columns shift. Decide these once, write them at
the top of `hex.rs` as a comment, and never deviate.

**Orientation: flat-top.** Matches the downloaded tileset, and matches what the
old Godot project was already doing (`tile_offset_axis = 1`). Note this is *not*
forced by the tileset — you render coloured pixels from M0 through M7 and the
tiles only matter at M8 — but it costs nothing, so take the free alignment.

**Offset convention: odd-q.** Storage stays a plain rectangular array indexed
`row * width + col`; flat-top hexes tile in columns, so odd-numbered *columns*
are shifted half a cell **down**. Red Blob Games calls this "odd-q offset" and
documents the axial conversion both ways.

**Axial `(q, r)` for all maths.** `q` is the storage column; `r` is the axial
row, which is *not* the storage row. Cube coordinates `(x, y, z)` where
`y = -x - z` are worth deriving for distance and rotation — they make several
formulas fall out trivially.

**The six neighbour directions in axial**, in a fixed order (N, NE, SE, S, SW, NW):

| | q | r |
|---|---|---|
| N | 0 | −1 |
| NE | +1 | −1 |
| SE | +1 | 0 |
| S | 0 | +1 |
| SW | −1 | +1 |
| NW | −1 | 0 |

The vectors are the same six as for pointy-top — orientation changes only which
compass label sits on each. Flat-top has no due east or west neighbour.

This mapping is verified, not assumed: under flat-top pixel layout
(`x = 3/2·q`, `y = √3·(r + q/2)`, with y increasing downward as in an image),
`(0,−1)` moves straight up and `(0,+1)` straight down, while the four remaining
vectors land on the diagonals as labelled.

Fix that order and keep it. Later stages store a flow direction as an index into
it, and if the order shifts under you every saved world becomes wrong.

### The one gotcha that will bite you

**Never do neighbour arithmetic in offset (row, col) space.** The offsets differ
between odd and even *columns*, and code that gets it right for one parity and
wrong for the other produces maps with a faint vertical banding you won't
consciously notice for weeks.

Always convert offset → axial, do the arithmetic in axial, convert back. It is
one extra step and it removes an entire category of bug.

## What to build

**`hex.rs`** — the only module that knows what a coordinate is.

- Offset ↔ axial conversion, both directions.
- Axial ↔ cube conversion.
- Distance between two cells.
- Neighbours of a cell, in the fixed direction order above, bounds-checked
  against the grid so edge cells simply yield fewer.
- Ring at radius *n*, and spiral (all cells within radius *n*).
- Line between two cells — not needed until M6, skip it if you'd rather.

Public API should hand back **flat `usize` indices**, per rule five in
[plan.md](plan.md). Axial coordinates are an implementation detail of this
module. This is what keeps the hex-versus-square decision cheap to reverse.

**`grid.rs`** — `Grid<T>`: width, height, a flat `Vec<T>`, indexing, bounds
checking, iteration over indices. Deliberately dumb. It should not know that the
lattice is hexagonal.
Note from user: I decided against this. It's over-engineering, and it will be trivial to write a square grid if I decide to switch to that.

**`rng.rs`** — a master seed, and derivation of a per-stage `ChaCha8Rng` by
hashing the master seed with a stage name. Get this right now; retrofitting it
means regenerating every reference world you've grown attached to.

**`render/png.rs`** — take a `Grid<f32>` and a colour ramp, write a PNG. At one
pixel per cell, write the array directly and ignore the half-cell column shift;
the shear is invisible at map scale. Add the shift only when you render cells
larger than a few pixels — for flat-top that means offsetting odd columns
downward, so it's a per-column vertical shear rather than a per-row horizontal one.

**`bin/worldgen.rs`** — `--seed`, `--size`, `--out`. Nothing else yet.

## Tests

The hex identities are the good ones: cheap to write, and they catch
off-by-ones that are otherwise invisible until they've corrupted three stages.

- Round-trip offset → axial → offset is the identity, for **every** cell in a
  non-square grid. Use a non-square grid deliberately — it catches transposed
  width/height, which a square grid hides.
- Distance from a cell to each of its six neighbours is exactly 1.
- Distance is symmetric, and distance from a cell to itself is 0.
- Neighbourhood is reciprocal: if B is a neighbour of A, A is a neighbour of B.
  Run it over every cell in a small grid.
- An interior cell has exactly 6 neighbours, all distinct, all in bounds.
- A ring of radius *n* contains exactly `6n` cells for *n* ≥ 1, and 1 at *n* = 0.
- A spiral of radius *n* contains exactly `1 + 3n(n+1)` cells.
- **Golden seed**: hash a generated field for a fixed seed and size, assert
  against a stored digest.

That last one is the whole reason M0 exists as a milestone. Write it here.

## The smoke test that's worth more than the unit tests

Render concentric rings — pick a cell near the middle, colour its rings at
radius 1 through 8 differently, write the PNG.

If the coordinate maths is correct you get clean, obviously hexagonal rings. If
anything is wrong — parity handling, a bad direction offset, a transposed
conversion — you get visible notches, gaps, or lopsided rings, and you'll see it
in a second rather than deducing it from a failing assertion three stages later.

Keep this renderer. It stays useful the whole project.

## Acceptance

M0 is done when:

1. `cargo run --release -- --seed 42 --out out/` writes an fBm PNG that looks
   like coherent noise, not static and not banding.
2. The same seed produces a byte-identical PNG across runs.
3. A different seed produces a visibly different one.
4. The concentric-ring PNG shows clean hexagonal rings.
5. The golden-seed test passes, and you have deliberately broken it once — flip
   a constant, watch it fail, put it back — so you know it actually guards
   anything.

Then start M1.
